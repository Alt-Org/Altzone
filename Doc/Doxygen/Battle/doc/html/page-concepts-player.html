Player Slots and Teams

Each Player has an assigned BattlePlayerSlot and a BattleTeamNumber.
The possible Slots are 1-4.
The Teams are TeamAlpha and TeamBeta.
Players in Slots 1 and 2 are in TeamAlpha and Players in Slots 3 and 4 in TeamBeta.
Guest and Spectator slots also exist, but are not currently used in Battle.
The enums for Player Slots and Teams are defined in {Quantum Simulation}.


Player PlayState

This concept extends the more general {PlayState} concept. However, this is tracked explicitly.
Each Player has a BattlePlayerPlayState used to track their state in the game, which is detached from {Player Character Entities} that the Player controls.
Each {PlayerSlot} has a Player PlayState associated with it including slots that have no player.
The general {PlayState} applies to the individual {Player Character And Shield Entities}.


Player Manager Data

Player data not connected to individual {Player Character Entities} is handled by {PlayerManager}.
The {PlayerManagerData} Quantum Singleton Component is used to store Player Data.
The {PlayerHandle} struct allows the code to access Player Manager Data of specific individual Players.
Player Manager Data is defined and used in {Simulation}.


Joining and Initializing

Quantum handles Players connecting to the game. The data from Quantum is used to initialize everything related to Players in the game. BattleGameControlQSystem receives Player information from Quantum when a Player joins and passes it to {PlayerManager}, which processes the Player's data and registers them as having joined.

Once all Players have joined, BattleGameControlQSystem tells {PlayerManager} to create {Player Character Entities} for all Players.


Player Input

Players can interact with the game through moving and rotating their {Player Character Entity}, as well as switching between their available {Player Character Entities}.
Player Inputs are processed and compiled into a Quantum Input Struct on the Unity/View side in {PlayerInput}. The created struct is passed over to Quantum Simulation.
Quantum synchronises the struct for all connected clients, and classes on the {Quantum Simulation} side use the contained data.

See Input🡵 Quantum's documentation for more info.


Player Character and Shield Entities

Each Player controls 3 Character Quantum Entities in the game, each of which have a {Character Number}.
For each Player one {Selected Character} can be present in the arena at a time and {PlayerManager} handles spawning and despawning Character Entities when switching between them.
Each Character has one or more Shields, each of which has a {Shield Number}. One of the Shields may be {Attached} to the Character. One or more Shields can also be present in the arena detached from the Character.
The {ShieldManager} handles Shield Entity management.
Each Character and Shield Entity has a {Player Character Class} that it belongs to.

These Entities are created based on Unity Prefabs. Entities are controlled by Quantum Simulation. The Unity Prefab root GameObject contains a Quantum Entity Prototype component, where the Entity is defined.

During gameplay the Player Character and it's Shield(s) exists both as a Quantum Entity inside {Quantum Simulation} and a Unity GameObject inside Unity View, which Quantum links together.

The Entity contains Quantum Components used by the Quantum Simulation. The most significant of these are the {PlayerData} and the {ShieldData}, which are our own defined data relating to Player Character and Shield Entities. Optionally, the Character Entity can have a Class Data Component.

See {Player Character Classes} for more info.

The Unity root GameObject has the child object PlayerViewModel ,or ShieldViewModel for Shields, containing all things related to the visible elements of Player Characters and Shields.
The attached {PlayerCharacterViewController} or {PlayerShieldViewController} component implements Unity View / Visual logic for Player Characters and Shields.

Player Character Number

Each Character Quantum Entity is internally assigned a Character Number between 0 and 2, each corresponding to one of the 3 Characters a Player controls. It is used to reference a specific Character for a given Player.


Player Character State

Each Character Quantum Entity always has a BattlePlayerCharacterState indicating if the Character is Alive or Dead.


Selected Character

The Selected Character is the Character Entity that is currently {InPlay}.
The Selected Character is tracked using {Player Character Number}.
This is managed by the {PlayerManager}.


Player Character Spawn Behaviour

Each Player Character has 3 ways to spawn, defined by BattlePlayerSpawnBehaviour.

Enumerator
DefaultPosition Character spawns in the position defined in the arena spec.
CharactersPreviousPosition Character spawns in the position it despawned in.
PreviousCharactersPosition Character spawns in the position the last character despawned in.

The {PlayerManager} handles spawning based on the Player Character's chosen Spawn Behaviour.


Shield Number

Each Shield Quantum Entity is internally assigned a Shield Number, each corresponding to one of the Shields a Character controls. It is used to reference a specific Shield for a given Character.


Attached/Detached Shield

Each Shield Entity can be Attached or Detached from the Character Entity they are bound to.
When Attached, the Shield Entity will move with the Character Entity.
When Detached, the Shield Entity will move independently from the Character Entity it is bound to.
Regardless of if the Shield Entity is Attached or Detached, it is tracked using the {Shield Number}.
This is managed by the {ShieldManager}.


Player Character Classes

Explanation

In Quantum Simulation, Player Character Classes function by having implementable methods that are called in certain situations during a game, such as when a projectile collides with a {Player Character Entity}. Classes can also implement an update method.

In Unity View, Player Character Classes function by having implementable methods that are called when certain events occur during a game, such as when the player takes damage. Classes can also implement an update view method.
Characters and Shields are separated in Unity/View, both of which can independently implement Class logic.

These methods can be used to implement functionality on top of the base logic, for example the default Simulation collision logic and/or Unity/View update logic, changing how different Character Classes function.

Implementation

In Quantum Simulation, every Player Character Class can optionally have a unique C# {PlayerClass}.
Character Classes can also optionally have a {PlayerClassQSpec} and {PlayerClassData} QComponent attached to the {Player Character Entities} for additional data the Class will use.
The C# {PlayerClass} are stateless and there is only one instance for each Character Class. These are loaded and managed by {PlayerClassManager}.

In Unity View, every Player Character class can optionally have a {PlayerCharacterClassViewController} and/or a {PlayerShieldClassViewController}.

Quantum simulation


Simulation Code Overview


Management

This section contains Quantum simulation side Player management related code, while the game logic is handled by the {Game Logic} code.


PlayerManagerData (Quantum Singleton)

The BattlePlayerManagerDataQSingleton struct is a Quantum Singleton Component defined in and generated from BattlePlayerManagerData.qtn containing all our defined data for Players. {PlayerHandle} is used to access this data for each individual Player.
The data contained in this Quantum Singleton Component is used by the {PlayerManager}.


PlayerManager

The BattlePlayerManager handles player management, allowing other classes to focus on gameplay logic.
Provides static methods to Initialize, spawn, despawn, and query player-related data.
Handles Initializing Players that are present in the game, as well as spawning and despawning {Player Character Entities} and also contains {Playerhandle} struct.

See {Joining and Initializing} for more info.

Player Entity Management

Characters can be {Alive} or {Dead} and {InPlay} or {OutOfPlay}.

A Character can be Spawned using SpawnPlayer. ({InPlay})
The Character is spawned based on it's chosen {Spawn Behaviour}.
If a Character is {Dead}, it cannot be Spawned.

A Character can be Despawned using DespawnPlayer. ({OutOfPlay})

The SpawnPlayer and DespawnPlayer methods also affect the {Player PlayState} of the Player the Character belongs to.


PlayerHandle

The PlayerHandle struct defined in {PlayerManager} allows the code to access {Player Manager Data} of each individual Player.

There is both a private PlayerHandleInternal struct containing all the data for use internally within {PlayerManager}, and the public PlayerHandle exposing some parts to the rest of the game.


ShieldManagerData (Quantum Singleton)

The BattlePlayerShieldManagerDataQSingleton struct is a Quantum Singleton Component defined in and generated from BattlePlayerShieldManagerData.qtn containing all our defined data for managing Shields.
The data contained in this Quantum Singleton Component is used by the {ShieldManager}.


ShieldManager

The BattlePlayerShieldManager handles {Shield Entity} management, allowing other classes to focus on gameplay logic.
Provides static methods to Initialize, {Attach}, remove and query shield-related data.
Handles Initializing Shields that are present in the game, as well as attaching and detaching Shield Entities from a Character Entity.

Shield Entity Management

Shields can be {Attached} or Detached and {InPlay} or {OutOfPlay}.

A Shield can be {Attached} to a player's Character using AttachShield. This has no effect on the {InPlay/OutOfPlay}.
If a Character already has a shield {Attached}, the shield will be swapped.
When {Attached}, {InPlay/OutOfPlay} logic is handled by the {PlayerManager}. ({InPlay} when Character is {InPlay}, {OutOfPlay} when Character is {OutOfPlay})

Shields can be used Detached using GetDetachedShieldEntityRef. The method will retrieve the shield to be used in the arena (Detached and {InPlay}) {Attached} or not, Detaching the Shield if needed.
A Shield can be Removed using RemoveShield, teleporting it out of the arena. (Detached and {OutOfPlay})
{Attached} or not, Detaching the Shield if needed.


Game Logic

This section contains Quantum simulation side Player gameplay logic related code, while the management is handled by the {Management} code.


PlayerData (Quantum Component)

The BattlePlayerDataQComponent struct is defined in and generated from BattlePlayerData.qtn. This contains data specific to each {Player Character Entity} used by the Quantum Simulation during gameplay.


ShieldData (Quantum Component)

The BattlePlayerShieldDataQComponent struct is defined in and generated from BattlePlayerShieldData.qtn. This contains data specific to each {Player Shield Entity} used by the Quantum Simulation during gameplay.


PlayerQSystem

The BattlePlayerQSystem contains the primary Quantum Player logic. This Quantum System contains code for handling collisions and the update method for {Player Character Entities}. Other classes are utilized for specific aspects of Player logic.

See {PlayerMovementController} for more info.
See {PlayerBotController} for more info.


PlayerMovementController

The BattlePlayerMovementController contains the primary UpdateMovement method which handles Player movement, and is called by {BattlePlayerQSystem}. Also contains individual helper methods for moving and rotating {Player Character Entities}, which can be used by other scripts.


Character Class Management and Game Logic

Each Player Character belongs to a {Player Character Class}.
This section contains Quantum simulation side {Player Character Class} management and game logic related code.


PlayerClassManager

The BattlePlayerClassManager handles the initial loading of {PlayerClasses} and routes individual game events to the correct Class scripts.
The {PlayerClasses} are stateless and there is only one instance loaded at a time.
Scripts such as {PlayerQSystem} call methods in PlayerClassManager, which then in turn call the corresponding method for the Character Class of the specified {Player Character Entity}.

See {Player Character Classes} for more info.


PlayerClass

Every Player Character Class can optionally have a unique C# class that inherits one of the two base BattlePlayerClassBase classes defined in BattlePlayerClassManager.cs. These classes can choose to implement any of the available methods for functionality. Character Classes can also optionally have a {PlayerClassData} QComponent for additional data.
When a Character Class has a Data QComponent, the C# class inherits the generic version of the base class using the Data QComponent as the generic type parameter.
Character Classes can also optionally have a {PlayerClassQSpec} for additional immutable data.
As stated before the C# class is optional and can be omitted for Player Character Classes that need no additional Quantum Simulation logic.

C# code example

// Without data QComponent
public class BattlePlayerClassExample1 : BattlePlayerClassBase
{
// ...
}
// With data QComponent
public class BattlePlayerClassExample2 : BattlePlayerClassBase<BattlePlayerClassExample2DataQComponent>
{
// ...
}

The C# classes are stateless and there is only one instance for each Character Class which are loaded and managed by {PlayerClassManager}.
Scripts such as {PlayerQSystem} call methods in {PlayerClassManager}, which then in turn call the corresponding method for the Character Class of the specified {Player Character Entity}. This way each Player Characters possible Character Class methods are always correctly called.

See {Player Character Classes} for more info.


PlayerClassData (Quantum Component)

Every Player Character Class can optionally have a Data QComponent for additional data.

Qtn code example

component BattlePlayerClassExample2DataQComponent
{
// ...
}

The Data QComponents are attached to the {Player Character Entities} and are used by the C# class of the corresponding Character Class.

See {PlayerClass} for more info.
See {Player Character Classes} for more info.

Every Player Character Class can optionally have a QSpec for additional immutable data that is shared between all the {Player Character Entities} of the corresponding Character Class.

PlayerBotController

The BattlePlayerBotController contains the GetBotInput method which handles Bot movement logic, and is called by {BattlePlayerQSystem}.
Bots have a base character which is retrieved from BattlePlayerBotQSpec using GetBotCharacters method.
In a match each Bot uses 3 instances of the base character.

View


View Code Overview

The Unity/View code is separated into Character and Shield logic.
Any Character related logic will start with BattlePlayerCharacter, while any Shield related logic will start with BattlePlayerShield.
Both Character and Shield logic use the {Player Character Class} term, which is separate from both and should not be confused with either. Player Inputs are also processed in the Unity/View code and is then sent over to Quantum.


PlayerInput

The BattlePlayerInput is processed and compiled into an Quantum Input Struct, which is passed over to the Quantum Simulation when polled by Quantum.

See {Player Input} for more info.


PlayerCharacterViewController

The BattlePlayerCharacterViewController handles Player Character Unity/View logic.
{PlayerCharacterClassViewControllers}, which are tied to this C# class, handle {Player Character Class} specific Unity/View logic.


PlayerCharacterClassViewControllers

Every Player Character Class can optionally have a View Controller which extends the BattlePlayerCharacterClassBaseViewController.
These View Controllers can be optionally implemented and attached to Player character viewmodel in prefab.
The PlayerCharacterClassViewController can choose to implement any of the available methods for functionality to handle Character Class Unity/View logic.
If no PlayerCharacterClassViewController is attached then BattlePlayerCharacterClassNoneViewController is attached.
As stated before the PlayerCharacterClassViewController is optional and can be omitted for Player Character Classes that need no additional Unity/View logic.
PlayerCharacterClassViewControllers are tied to {PlayerCharacterViewController}.

C# code example

public class BattlePlayerCharacterClassExampleViewController : BattlePlayerCharacterClassBaseViewController
{
// ...
}

See {Player Character Classes} for more info.


PlayerShieldViewController

The BattlePlayerShieldViewController handles Player Shield Unity/View logic.
{PlayerShieldClassViewControllers}, which are tied to this C# class, handle {Player Character Class} specific Shield Unity/View logic.


PlayerShieldClassViewControllers

Every Player Character Class can optionally have a View Controller which extends the BattlePlayerShieldClassBaseViewController.
These View Controllers can be optionally implemented and attached to Player shield viewmodel in prefab.
The PlayerShieldClassViewController can choose to implement any of the available methods for functionality to handle Character Class Unity/View logic.

As stated before the PlayerShieldClassViewController is optional and can be omitted for Player Character Classes that need no additional Unity/View logic.
PlayerShieldViewControllers are tied to {PlayerShieldViewController}.
